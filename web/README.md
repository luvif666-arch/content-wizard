# 内容创作向导 · 网页版

把《如果你做不好内容，大概率也聊不好天》里那条「像聊天一样做内容」的思维链，固化成一个可以点着走完的六步网页程序。终点不是成稿，是一份**能直接发给 AI Agent 的创作简报**。

左侧是六步向导，右侧是**草稿箱**——可以同时存多份草稿，自己决定留哪一份。

- 在线使用：<https://luvif666-arch.github.io/content-wizard/>
- 本地运行：<http://127.0.0.1:5240/>（静态服务）
- 纯前端，不接后端；不填 API Key 也能完整走完六步。

---

## 快速开始

```bash
cd web
npm install --ignore-scripts      # Windows 沙箱下需加 --ignore-scripts，见下方说明
npm run build                     # 产出 dist/
npm run serve                     # http://127.0.0.1:5240/
```

开发模式：

```bash
npm run dev                       # http://127.0.0.1:5233/
npm run typecheck
npm run verify                    # 端到端验收（需要先 npm run serve）
npm run verify:drafts             # 草稿箱 + 「候选重生成即清空」专项验收
```

> **端口说明**：已经构建好的版本固定跑在 `5240`（用 `npm run serve`）；开发模式用 `5233`（`npm run dev`）。两者分开是为了让「验收构建产物」和「改代码时的热更新」互不干扰。

> **安装说明**：在受限沙箱里 `npm install` 会因为安装脚本 spawn 子进程被拒（`spawn EPERM`）。加 `--ignore-scripts` 即可；本项目依赖里没有必须执行的 postinstall。同理，`vite build` 需要 esbuild spawn 子进程，受限沙箱下会被拒，需要在允许子进程的环境里构建。

## 六步流程

| 步 | 层 | 问什么 | 交互 | 出路 |
|---|---|---|---|---|
| 1 | 关系 | 这条内容是给谁看的 | 单选 5 类受众，或自己描述 | 确立语境基线 |
| 2 | 话题 | 你想聊哪个大方向 | 输入大类 → 给候选子话题卡片，最多选 2 | 收窄讨论范围 |
| 3 | 选题 | 这次你要对谁说什么 | 「具体的人」单选 + 「具体的事」填空，**两者必填** | 自动生成「这次不讲什么」清单 |
| 4 | 切入点 | 这次从哪里开始聊 | 6 类各给一个结合当前选题的候选，选 1–3 并排序 | 入口顺序 + 一致性校验 |
| 5 | 标题 | 用哪句话开启这段对话 | 问题式 / 判断式 / 共鸣式各 1 条，**每条附生成理由** | 选定标题 |
| 6 | 表达 | 你准备用什么让对方理解 | 三段结构可增删改序 + 体裁（图文 / 口播视频 / 多图轮播）；**每一段给 3–4 条结合已定内容的参考写法，可一键扩写** | 大纲 + 每段写法 + 体裁追问 |

## 草稿箱

工作区是左右两栏：左边六步向导，右边草稿箱。窄屏（< 1000px）下草稿箱折叠成顶部入口 + 右侧抽屉，不挤占主流程。

- **自动保存**：每写一步都直接落进当前草稿，没有「保存」按钮。
- **一份多项**：新建、打开、重命名、删除（删除要二次确认）。
- **每项显示**：标题、已完成几步（如 `3/6`）、最后编辑时间。
- **标题规则**：自动取「大方向 + 子话题」（如 `情感 · 约会`），还没有话题时用「未命名草稿」；一旦手动重命名，就不再被自动标题覆盖。
- **导出后不自动清掉**：走完六步、导出简报之后，草稿仍留在草稿箱里，删不删由你决定。
- **顶部常驻「＋ 新建草稿」**：没做完也能先把手上这份存下来再开新的。

### 切草稿为什么不会串味

两层保证：

1. **状态按草稿隔离**——每份草稿各自持有一整份 `WizardState` 和一份「已确认」快照，改动只会写回当前草稿。
2. **组件随草稿重挂载**——工作区子树的 `key` 绑定当前草稿 id。步骤组件里有不少本地状态（第 2 步的输入框、第 6 步已生成的参考写法），只靠 props 更新是清不掉的，重挂载才能保证「新草稿的话题不会配着旧草稿的切入点」。

## 四条核心机制

### 1. 候选生成：预设优先，模型兜底

每一步的候选项按 **内置库 → 规则模板 → 模型生成** 的顺序取，任何一环失败都往下回退：

- 第 2 步：命中预设话题表（情感 / 职场 / AI / 健康 / 消费 / 自媒体 等 14 类）就直接用；没命中且有 API Key 才问模型；模型失败再回退到规则推导，**保证永远不出现空白**。
- 第 4、5 步：模型不可用时按规则模板拼装，所以断网也能走完。
- 第 6 步：默认由「内置库写法 + 按当前选题/切入点/标题现拼的模板」组成。
- 界面上会如实标注候选来源（「内置库」/「模板推导」/「模型生成」），不假装查过。

### 2. 失效传播：改上游，下游必须重新确认

每一步确认时，会把「它当时依赖的上游答案」序列化成快照存下来。之后只要上游变了，这一步就标记为**待确认**，进入该步时显示横幅要求重新确认，不静默沿用旧答案。

判据是「**这一步有没有确认过的快照**」，而不是「本次会话走到哪」——否则刷新页面后，已经确认过的下游步骤会被静默当成仍然有效。

### 3. 候选重生成 ⇒ 旧选择立即作废清空

这和上一条是**两件不同的事**，代码里也刻意分开：

| | 触发 | 处理 | 为什么 |
|---|---|---|---|
| **待确认** | 用户已经确认过这一步，但上游动了，而这一步的答案仍然保留 | 保留答案，标「待确认」，让他决定要不要沿用 | 答案是他的，参照物还在，只是语境变了 |
| **作废清空** | 这一步的**候选本身换了一批**（上游改了，或用户点了「换一批」） | 立即清空，并说明「哪一项变了、原来的什么已经不适用」 | 选项都换了，旧答案连参照物都没有，留着只会误导 |

落地方式：给每一批候选记一个「依据」（真正影响这批文案的上游字段）。依据对不上就清空，并把差异翻译成人话——例如改完选题回到第 4 步会看到：

> 选题变了，原来的切入点已经不适用，已清空，请重新选。

分两步的判据：

- **在应用里选过的**（记过依据）⇒ 依据对不上就直接清空，不看文案是否碰巧相同；
- **没有记录依据的**（旧版草稿 / 从 JSON 恢复 / 分享链接进来）⇒ 退化为「文案还在不在候选里」，还在就补记依据、不在才清空——导入的数据不该一进来就被判废。

两个例外是刻意的：

- **自己手写的标题不清**：它的参照物是用户的判断，不是候选，所以保留并走「待确认」，让他决定要不要改。
- **第 6 步的用户正文不清**：只作废「从候选里采纳的参考写法 / 扩写」，用户自己敲进「这一段你要讲什么」的内容一律保留。第 2 步同理：大方向改了会清掉已选子话题，但清的是这一步自己的字段，不整步重置（否则会把他刚敲的大方向一起弄丢）。

### 4. 切入点一致性校验

文章里最容易被程序忽略的一条：**切入点只负责把人带进来，后面的内容必须继续完成选定的目标**。所以第 4 步选了「普遍误区 / 一次踩坑 / 两类人对比」这类纯信息型入口时，会提醒正文必须回到第 3 步的目标，需要用户确认才继续；选了「具体场景」这类入口则不打扰。

  已选切入点：0 个（应为 0）
  清空说明：选题变了、话题变了，原来的切入点已经不适用，已清空，请重新选。

### 专项验收：灵感示例的覆盖度

`node verify-coverage.mjs` 故意用一个**内置预设库覆盖不到**的话题（默认「宠物殡葬」）跑第 3 步，确认不会退化成空白或通用模板：

```
PASS  「宠物殡葬」能给出子话题候选 — 入门 / 常见误区 / 真实成本 / 第一步
PASS  第 3 步仍给出 4 条以上示例（不是空白）
PASS  示例与当前话题真正相关，不是通用模板
PASS  示例覆盖多种不同处境
PASS  来源如实标注（模板拼出来的不冒充内置文案）— 「模板推导」
```

这条验收暴露过一个真问题：示例明明是用话题 + 通用句式**现拼**的，来源却标成了「内置预设」。现在统一定义为四档来源，不再夸大准确度：

| 标注 | 含义 |
|---|---|
| 内置库 | 预先写好的成稿文案（灵感示例覆盖约会 / 暧昧期 / 长期关系 / 转行 / 育儿；第 6 步的三段各有一条内置写法） |
| 模板推导 | 用当前话题、选题、切入点、标题 + 通用句式**现拼**，覆盖任意话题 |
| 模型生成 | 你配置的模型按当前上下文生成，不是搜索结果 |
| 联网检索 | 真的联网查过才会用；**当前没有实现**，所以不会出现 |

应用是浏览器直连 OpenAI 兼容端点，**没有联网检索能力**。`CandidateSource` 里预留了 `search` 和「联网检索」标签，但当前没有任何路径会产生它——**不会在没有联网时标成联网**。

### 第 6 步的「参考写法」

结构选完、体裁选完之后，人还是会卡在「这一段具体写什么」。所以每一段都配：

- **3–4 条候选参考写法**，按当前结构逐段生成，每条都带上第 3 步的「对谁说什么」、第 4 步的切入点、第 5 步的标题，让它像「这条内容的这一段的写法」，而不是通用模板；
- **「换一批」**：模板来源本地位移轮换，模型来源重新请求；换一批即视为候选更换，已采纳的写法同时作废并说明原因；
- **「根据已定内容扩写这段」**：展开成「这一段打算讲什么 / 举什么例子 / 给什么建议」，可一键把「打算讲什么」写进该段的正文说明；
- **来源逐条标注**，并明说这是**参考不是成稿**：可以采纳，也可以照着全改。
- 例子一律提示用户用自己的经历填——**不替他编**。

### 导出设计：三种载体，两种意图

三种导出（Markdown / 提示词 / JSON）都从同一个 `buildBrief()` 渲染，所以内容必然一致，不靠人工同步。它们的区别在**用途**：

- **Markdown** —— 离开页面之后还能用：进笔记软件、进 git、发给别人协作。是交付物。
- **提示词** —— 带指令（「按这个写，切入点只负责开头，后面必须回到选题目标」），把简报变成指令，直接发给 AI。
- **JSON** —— 给程序读的结构化快照，面板上那张卡片给不了任何程序。它还能**粘回来继续改**（`lib/import.ts`），是可归档、可续编的存档。

界面上动作跟着当前标签走（预览哪个就复制/下载哪个），而不是把每种格式都堆一对按钮。

### 其他优化

- **勾选符用 CSS 绘制而不写进 DOM**：否则读屏软件会把选项念成「✓约会」，按文本定位的自动化测试也会失配。
- **调试钩子只在 `?debug=1` 时挂载**：公开页面上不存在 `window.__wizardDebug`（里面有草稿箱概览、快照与失效标记，便于验收排查）。
- **已选范围做成可删减的标签**：候选列表会随输入变化，自定义添加的分支原本没有任何删除入口，一旦加错就去不掉。现在统一在「已选范围」里删减：点 × 去掉一项、清空重选，点候选卡片也能取消。
- **「新建草稿」不复用 `.btn.primary`**：页面上的 `.btn.primary` 始终是「这一步的主操作」，自动化验收也按这个约定定位；顶部入口用独立的 `.btn.new` 样式，同样显眼但不抢语义。
- **导出简报后不再清空草稿**：原先「从头开始一份新的」会把手上这份直接抹掉——这正是「没做完想换个话题却没法存下来」的来源。现在它变成「新建一份草稿，这份留在草稿箱」。

### 验证过程中发现并修掉的四个真实 bug

1. **第 2 步输入大类话题没有回写父状态** —— 导致「是否填过话题」判断不到，提示错误地显示「还没填大类话题」。
2. **拦截提示跨步骤残留** —— `blockMsg` 没有绑定步骤，翻到下一页还在显示上一页的拦截原因，误导用户。
3. **刷新后漏报「待确认」** —— 原先用「本次会话走到哪」抑制警告，刷新后该值归零，已确认的下游步骤被静默当成有效答案。改为以「是否有确认快照」判定。
4. **改了话题/选题后，第 4 步仍留着旧话题的切入点文案** —— 原来的 `useEffect` 只重新生成候选，从不处理已选；而 `value.selected` 存的是旧候选对象的**拷贝**，所以永远不会自己更新，必须手动取消再重新勾选。现在改成：候选一重生成，基于旧候选的选择立即作废清空，并说明原因（见「四条核心机制」第 3 条）。复现脚本 `probe-stale-angle.mjs` 保留在仓库里。

## 明确不做（避免范围膨胀）

- 不做账号系统、云同步、多人协作。草稿箱只存在这台设备的 `localStorage` 里，换浏览器/换设备不会同步；要搬走用简报的 JSON 导出。
- 不直接生成成稿或封面图——向导的价值在于把中间那层「想清楚」，成稿交给任何 AI 都能写。
- 不接入任何平台的实时热榜数据。
