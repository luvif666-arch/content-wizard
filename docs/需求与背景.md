## 1. 文章到底讲了什么（先对齐，再动手）

作者的核心主张只有一句：**做内容就是跟一个人聊天**。她用一个「约会」例子，把创作者嘴里混着用的几个词拆成了可以逐层收敛的链条：

| 层级 | 定义（文章原意） | 一句话检验 |
|---|---|---|
| 内容 | 用户看到、听到、感受到、理解到的**总和**（含标题、封面、评论区） | 它是个容器，不是其中一个零件 |
| 话题 | 准备聊的**范围** | "我想做情感内容" —— 范围有了，但我还是不知道你要讲什么 |
| 选题 | **这次对谁说、说什么**，必须有一个具体的人 + 一件具体的事 | "对第一次见网友的人，讲怎么让这次约会聊得舒服" |
| 切入点 | 这次**从哪里开始聊**（入口） | "从选哪家餐厅开始" |
| 标题 | 用来**开启这段对话**、最有吸引力的一句话 | 让对的人愿意点进来 |
| 表达 | 怎么把这句话展开成完整叙事（场景→解释→建议） | 知道对方理解到哪，把下一步接给他 |

三个最容易被忽略、但对做成程序最关键的点：

1. **「切入点」是作者单独拎出来强调的概念**（她说这是栋哥原帖没提到的）。它和选题不是一回事：选题决定"说什么"，切入点决定"从哪进来"。同一个选题换切入点，要准备的例子、信息和表达顺序全都变。
2. **切入点只负责把人带进来，后面的内容必须继续服务于第 3 步选定的目标**。如果从"餐厅"切入却只写了一篇餐厅推荐，那它已经变成另一篇内容了。这是全流程里最需要程序去守的一条约束。
3. **词句长什么样，不能单独决定它属于哪一层**，要看它在这次创作里承担什么结果。所以"第一次约会应该去哪里吃饭"这句话，在策划阶段是选题，放到用户面前就是标题。→ **结论：程序里不要把某句话绑定到某个字段，要绑定到"它负责什么"。**

作者还给了故障排查表（第 07 节），这张表其实就是向导的"用户从哪一步开始卡住"分流依据：

| 症状 | 真正卡住的层 |
|---|---|
| 打开文档没话说 | 选题不具体 → 回到「对谁说什么」 |
| 一开口只能讲大道理 | 没有切入点 → 找一个具体场景 |
| 正文黏黏糊糊 | 表达层：例子、解释、语序不够 |
| 想说的都清楚了但没人点 | 标题层：力度不够 |
| 反复改标题却越改越乱 | 上游（选题/切入点）根本没定 |

## 2. 逻辑 → 程序：映射与流程设计

### 2.1 从"聊天"到"状态机"

文章里跟陌生人吃饭的顺序，本身就是一条天然的线性流程：

```
抿一下关系 → 找共同话题 → 挑他正在经历的事 → 按他知道多少决定从哪接话
   ↓            ↓               ↓                        ↓
 受众定位      话题范围        选题（对谁说什么）        切入点
                                                    ↓
                                            用哪句话开口（标题）
                                                    ↓
                                            怎么把话讲完（表达）
```

对应成程序的 6 步，**每步只问一个问题，绝不同屏暴露后续步骤**：

| 步 | 层 | 问什么 | 输入方式 | 产出 |
|---|---|---|---|---|
| 1 | 关系 | 这条内容给谁看 | 单选 + 自定义 | 语境基线 |
| 2 | 话题 | 想聊哪个大方向 | 自由输入 → 系统给 4 个候选 → 最多选 2 | 讨论范围 |
| 3 | 选题 | 这次对谁说什么 | 两段式表单（具体的人 + 具体的事） | 选题句 + 「这次不讲什么」清单 |
| 4 | 切入点 | 这次从哪里开始 | 6 类各生成 1 个候选，选 1–3 并排序 | 入口 + 一致性警告 |
| 5 | 标题 | 用哪句话开启对话 | 三种句式各 1 条 + 生成理由 | 标题 + 邀请对象说明 |
| 6 | 表达 | 怎么让对方理解 | 结构（场景/解释/建议）+ 体裁 | 大纲 |

> 详细字段、选项、校验规则、兜底策略已写成机器可读文件：`flow.json`。它既是可以直接给程序读的配置，也是给 Agent 看的精确规格。

### 2.2 用户原话 → 精确需求

你说的原始意图：

> "先问哪个话题，用户输入大类话题，我们可以根据话题提出相关内容供其选择，之后仿照这类逻辑，慢慢深入切入点"

这句话在程序里的准确表述是：

> **第 2 步用「自由输入 + 系统给候选」的混合输入模式（free-text-then-suggest）：用户输入大类话题后，系统返回 N 个候选子话题卡片供选择；同一步的候选生成顺序为「内置预设映射表 → 向量/关键词匹配 → 模型生成」，任何一环失败都往下回退，最终都允许用户自己输入。后续第 4 步的切入点复用同一套「给候选 + 可自定义」的交互模式，不再重新发明。**

这里有个容易踩的坑，提前说明：**"话题 → 子话题"如果完全交给大模型，每次结果都不一样，用户会觉得这个工具不靠谱**。所以 `flow.json` 里把预设映射表放在第一位，模型只负责"没命中时补候选"。

### 2.3 三个必须写进程序的硬约束

1. **上游改动必须让下游失效**。用户在第 3 步把"第一次见网友的人"改成"约过很多次却进不了关系的人"，那么第 4、5 步原来的答案已经不成立了。程序必须把它们标成"待确认"，而不是静默沿用。
2. **切入点与选题的一致性校验**。第 4 步选完切入点后，检查它能否通向第 3 步的目标，不能就警告并要求确认——这是文章里唯一一处作者反复强调、但很容易被程序忽略的约束。
3. **无 Key 可用**。预设库 + 规则模板必须能独立跑完全流程，模型只是增强项。

### 2.4 最终产出

一份**创作简报**（不是成稿），六个区块：关系 / 话题 / 选题（含不讲什么）/ 切入点 / 标题（含理由）/ 表达结构与体裁。提供"复制全文""复制为 Agent 提示词""导出 Markdown / JSON""分享链接"。

**为什么产出是简报而不是成稿**：向导的价值在于把中间那层"想清楚"，成稿交给任何 AI 都能写；反过来，如果向导直接出稿，用户会跳过思考，回到"收藏一堆选题但写不出东西"的原点——那正是这篇文章要解决的问题。

- **`Content-Brief-Generator` 系列**（`agniiva/*`）全是 SEO 向：爬 SERP、分析排名、生成 SEO 大纲。和"内容创作思维流程"不是一回事，只能参考它的 brief 字段设计。
- **通用表单/向导组件**：`kflorence/jquery-wizard`（支持分支）、`juanumana/steps-wizard-react`（2021 年的模板）都很旧。**如果只要做 6 步固定流程，不要引第三方向导库**，自己写一个 step 状态机更简单可控。

## 4. 两条落地路线，怎么选

**路线 A：网页小程序**（你原话的方向）
- 形态：本地跑或部署的 Vite + React 单页应用。
- 适合：你自己和团队用，想要可视化、能分享链接、能导出简报。
- 工作量：核心流程 1–2 天可跑通（先用预设库，不接模型）。

**路线 B：Agent Skill**（和我正在跟你对话的这套机制同构）
- 形态：一份 `SKILL.md` + `flow.json`，装进 Claude Code / Codex / DSH。
- 适合：你本来就在用命令行 Agent 干活，不想再开一个网页。
- 工作量：把现有两个文件改写成 SKILL 格式，半天内可用。
- 参考：[anthropics/skills](https://github.com/anthropics/skills)、[xiaohongshu-assistant](https://github.com/XunMengWinter/xiaohongshu-assistant) 的 `AGENTS.md` 写法。

**我的建议**：先做路线 A 的"纯预设库版本"（不接模型，6 步 + 导出能跑通），验证流程本身顺不顺；流程确认没问题后再接模型候选生成，并把同一套 `flow.json` 复用给路线 B。

## 术语提示

- **[结构化输出（Structured Output）](https://vibe-hub.org/structured-output)**：要求 AI 按事先约定的栏目和格式返回结果，而不是一段自由文本；前端靠它才能稳定地把候选渲染成卡片——`flow.json` 里的 `modelContract` 就是为它准备的。
- **[数据校验（Validation）](https://vibe-hub.org/data-validation)**：在使用输入前检查它的格式、范围和业务规则。这里指第 3 步"具体的人 + 具体的事"必须都填才能进入第 4 步，以及选项数量上限这类规则。

另外两个概念 VibeHub 暂无对应词条，我用自己的话说明：**向导式流程（Wizard）** 是把复杂任务拆成若干步、每步只让用户做一个决定并按顺序前进的交互模式；**状态机（State Machine）** 是用"有哪些状态、状态之间怎么跳"来描述程序，而不是用一堆 `if` 堆页面——本文里"改动上游就让下游全部失效"正是它的典型用途。
